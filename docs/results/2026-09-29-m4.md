# M4 results: libzstd level-9 ratio on the GPU

Date: 2026-09-29 · Commit: `ee82d65` (branch `m4`) · Block size: 128 KiB

## Setup

- **Hardware:** AMD Ryzen 9 9950X3D (16C/32T) and NVIDIA RTX 5090 (Vulkan, wgpu 30), Linux.
- **VRAM budget:** 6144 MiB. That fits an 8 GB card, but all throughput numbers were measured on the 5090.
- **Machine state:** a SkyrimSE session from another project was running when measurement was due. It had exited by the time the runs started (the snapshot is in `out/m4-load.txt`). Two idle QEMU VMs and the desktop kept running throughout, with load average about 1–2.
- **Corpus:** `data/corpus --ext dds,nif`, 6.49 GB real bytes, 51216 blocks. DDS is 95.6 % of it and NIF 4.4 %.
- **Metrics:** throughput is real bytes / s with MB = 10^6. Ratio is real bytes / compressed bytes.

## Headline

| Engine | Config | MB/s | Ratio | DDS | NIF |
|---|---|---:|---:|---:|---:|
| libzstd, 8 threads | **L9** | 669 | 1.3532 | 1.342 | 1.637 |
| **GPU** | **lvl9** (b1638 i3, 6144 MiB) | **1611** | **1.3549** | 1.344 | 1.654 |
| GPU `--verify` | lvl9 | 1608 | 1.3549 | | |

**M4's goal is met.** The GPU matches libzstd L9 on ratio (+0.13 %) and every frame decodes correctly with libzstd. It also runs at **2.4× the throughput of 8 CPU threads at L9**, above the 10 Gbit line, before any speed work.

## Per rung: GPU compared with the matching libzstd level

| Our preset (algorithm) | GPU MB/s | GPU ratio | CPU oracle, 8T (MB/s / ratio) | libzstd level | libzstd 8T MB/s | libzstd ratio |
|---|---:|---:|---:|---|---:|---:|
| lvl3 (dfast, mm5, greedy) | 1447 | 1.2711 | 449 / 1.2711 | L3 | 3927 | 1.2668 |
| rung1 (4-byte chain, depth 8, greedy) | 1961 | 1.3432 | 253 / 1.3432 | L5 | 1114 | 1.3452 |
| rung2 (… lazy) | 1788 | 1.3516 | 245 / 1.3516 | L6 | 925 | 1.3497 |
| lvl9 (… depth 32, lazy2) | 1611 | 1.3549 | 109 / 1.3549 | L9 | 669 | 1.3532 |

libzstd L4, L7 and L8 at 8 threads: 2101 / 1.3342, 843 / 1.3520 and 812 / 1.3525.

On a single thread (first 500 MB), libzstd reaches 580 (L3), 285 (L4), 146 (L5), 125 (L6), 115 (L7), 111 (L8) and 94 (L9) MB/s.

- **At the 10 Gbit line (≥ 1250 MB/s) with 8 threads on this CPU:** the best libzstd option is L4 at 1.334. The GPU gives 1.343 with rung1 at 1961 MB/s, or 1.355 with lvl9 at 1611 MB/s. That is 0.7 % and 1.6 % more compression.
- **On a typical 8-core PC,** assuming about 60 % of this CPU's per-core speed (an assumption, not a measurement), 8 threads would manage about 1370 MB/s at L4 and about 450 MB/s at L9.

For lvl9, end-to-end throughput is 1611 MB/s against 1819 MB/s for the kernels alone, so about 11 % goes to host and transfer overhead. The shares of GPU time for lvl9 are:

- **K3** (sequential parse, one thread per block): 55 %
- **K1** (tiled bitonic sort, per-block serial tile loop): 21 %
- **K2** (32-deep chain walk): 15 %

The speed phase targets these.

## Notes

- **The quadratic worst case in the lazy deferral chain has been reviewed and parked.** Simulated adversarial inputs stay at ≤ 6 byte compares per byte. The theoretical bound needs offsets that diverge at every step (see the Task 5 review in the SDD ledger). It should be re-checked for TDR headroom on slower GPUs.
- **`MAX_SEQS` is now sized for min_match 4 for every preset.** That costs lvl3 about 2 % of batch capacity: b1365 instead of b1388 at i3.
- **lvl3's end-to-end throughput fell from 1571 MB/s (M3) to 1447 MB/s here, with the kernel sum unchanged (~102 ms/batch, 101.7 ms above vs. M3's own number).** The smaller batch (b1365 vs. M3's b1388) accounts for about 2 % of that. The rest is host/transfer overhead going from roughly 9 % of wall time in M3 to roughly 14 % here (1447 / 1680 kernel-only MB/s ≈ 0.86), or measurement noise from the shared machine (see Setup). Neither has been isolated yet; both should be re-measured back to back at the start of the speed phase before attributing the gap to any one cause.
- **L9 gap analysis.** The GPU beats libzstd L9 slightly on ratio (NIF 1.654 vs. 1.637, DDS 1.344 vs. 1.342), which is somewhat surprising for a from-scratch reimplementation of the same algorithm shape. Plausible reasons, in no particular order and not verified against the reference source line by line — these are hypotheses, not conclusions:
  - **Full-length extension of capped matches.** K2's `find_best` reports lengths capped at `search_cap` during the search, but the parse always extends a capped hit to its true length (`match_len`) before deciding; if libzstd's search-time capping and length bookkeeping differ in some edge case, our extension could occasionally see (and pick) a longer match than L9 does at the same position.
  - **A hash chain vs. zstd's row-hash matcher.** L9 in real libzstd uses the row-hash match finder above a size threshold, which searches a *bounded number of rows* rather than walking a full predecessor chain; our GPU match finder walks the chain directly to `depth`, which could occasionally find a better candidate the row matcher's row-bounded search misses.
  - **16-bit hash.** `HASH_BITS = 16` (65536 buckets) is a specific choice that may distribute keys differently than whatever width/formula libzstd's L9 hash uses, changing which candidates collide (and therefore end up chained together) at the margins.
  - **Per-position K2 search with no lazy-skipping.** K2 searches every position's chain regardless of how recently a long match was found; libzstd's `lazySkipping` (see `zstd_lazy.c`) skips hash-table insertion (not matching, but chain population) after a run of short/incompressible steps, which could leave *its* chains sparser than ours at some positions, changing what's found later.

  None of these have been isolated with a targeted A/B test; they're recorded here as the working hypotheses for anyone chasing the gap further.

## Reproduce

```sh
B="cargo run --release -p gzc-bench --"; C="--input data/corpus --ext dds,nif"
$B cpu $C --levels 1,2,3,4,5,6,7,8,9 --threads 8 --out out/m4-cpu8
$B cpu $C --levels 3,4,5,6,7,8,9 --threads 1 --max-bytes 500000000 --out out/m4-cpu1
$B ref $C --preset lvl3,rung1,rung2,lvl9 --threads 8 --out out/m4-ref
$B gpu $C --preset lvl3 --batch 1365 --inflight 3 --out out/m4-gpu-lvl3
$B gpu $C --preset rung1,rung2,lvl9 --batch 1638 --inflight 3 --out out/m4-gpu
$B gpu $C --preset lvl9 --batch 1638 --inflight 3 --verify --out out/m4-gpu-verify
```
