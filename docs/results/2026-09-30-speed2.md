# Speed phase 2 results: 10.6 GB/s at libzstd-L9 ratio, 64 KiB blocks

Date: 2026-09-30 · Branch `speed2` @ `fe64d2c` · **Block 64 KiB** (the new maximum; blocks independent) · Budget 6144 MiB
RTX 5090, full corpus (`--ext dds,nif`, 6.49 GB, 100754 blocks), `--batch max --inflight 3` (b5403), medians.
Two idle QEMU VMs were running (load average 6–9, bursty), so the end-to-end numbers are host-sensitive; see below.

## Headline

| Preset (what it is) | Ratio | MB/s (median) | Runs |
|---|---:|---:|---|
| libzstd L9, reference (CPU) | **1.3379** (target) | 1754 on 32 threads | – |
| lvl9 (lazy2 d32, hash chains) | 1.33932 | 5767 | 5767 / 5865 / 5762 |
| lvl9seg (+ 4 KiB segmented parse, E1) | 1.33931 | 8809 | 8809 / 8793 / 8814 |
| **lvl9s12seg** (+ 12-bit bucket-sorted finder, E2) | **1.33926** | **10588** | 8 runs: 10360–10631 |
| **lvl9s12d16seg** (+ depth 16) | **1.33860** | **10652** | 5 clean runs: 10483–10868 (two earlier runs hit a load burst: 6959, 5735) |
| lvl9s12seg, subgroups off (portable floor) | 1.33926 | 8722 | 1 run |

Compared with the start of speed phase 2 (`master` 6bedcff at 64 KiB: lvl9 5374 MB/s), the fastest preset is
**1.98× faster** at an unchanged ratio class. The ratio stays above libzstd L9 on the same 64 KiB blocks. Every
preset is byte-identical to its CPU oracle: `--verify` passed, and 4000-block per-frame differential tests ran.

For the 10 Gbit use case (1250 MB/s), this is **8.5× line rate** on the dev GPU.

## What each experiment contributed (64 KiB)

| Step | Change | Effect |
|---|---|---|
| Block size 128 → 64 KiB (user decision) | Twice as many blocks per batch | lvl9 4107 → 5374 MB/s; ratio target now 1.3379 |
| **E1** segmented parse (`lvl9seg`) | Independent 4 KiB parse segments, one lane each; final pass re-encodes offsets with the true reps. Ratio −0.001 % | K3 20.9 → 6.4 ms/batch; **+31.5 %** |
| **E2** bucket-sorted finder (`lvl9s12*`) | Per-block counting sort on a 12-bit key in workgroup memory; K2 walks same-key runs. `depth 16` variant (E4) | K1 14 → 6 ms/batch; **+17 %**, +22 % with d16 |
| **E3** host and queues | E9: K2/K4/K5 without runtime bounds checks. E8: kernels read the upload buffer directly (−320 MiB). Readback on a dedicated Vulkan copy queue (wgpu-hal + ash), overlapping the next batch | **+27–33 %** |
| Rejected with numbers | Second async compute queue (the driver overlaps only if K1 launches first: 1.00–1.19×); 13-bit key (no better than 12 at 64 KiB); segment sizes 2 and 8 KiB | – |

## Where the time goes now

lvl9s12seg, b5403, per batch:

| Kernel | ms |
|---|---:|
| k1_sort | 6.5 |
| k2_window | 10.8 |
| k3_parse (segmented) | 6.7 |
| k4_entropy | 1.8 |
| k5_huffman | 5.0 |
| **Sum** | **30.7** (11.1 GB/s kernel-only) |

The host pipeline thread writes uploads (14.7 ms/batch) and delivers frames (14.9 ms/batch). The GPU waits only
2.3 ms/batch. **The pipeline is now host-bound**, which also explains the run-to-run noise under VM load bursts.
The next speed-up is on the host: parallel frame delivery, and letting the caller hand in and take out buffers
directly (R8's zero-copy intake/output API). Further kernel work would not show end to end.

## Research phase (10 agents)

Ten reports, each a different lens: ceilings, CUDA, Vulkan, parallel parse, match finders, data movement, small
GPUs, system, DDS domain and contrarian. They are synthesised in `docs/superpowers/speed/speed2-synthesis.md`.
Not yet built from that list:

- **Small-GPU defaults (R7):** K1 groups from residency, BPW = 2 on NVIDIA, heaviest-first ordering, a
  `--proxy 4060` mode.
- **K5 fix (R1, R7).**
- **Buffer sharing by lifetime (R6).**
- **Per-format DDS preset (R9):** measured ratio 1.3582 at 128 KiB with about ⅓ of the K2 work; to be re-measured
  at 64 KiB.
- **CUDA proof of concept (R2):** deferred.

**Dead ends, all measured:** frame-level sliding windows (rejected: blocks must stay independent), adaptive
per-block level, pre-classification, position-parallel parse, suffix-array/BT finders, hand-written SPIR-V, RT
cores, tensor cores and NPUs (`.superpowers/m5/m5-rt-npu.md`), and DPX instructions (Hopper-only in hardware;
compiled to plain `IADD`+`IMNMX` on sm_89/sm_120).

## Known follow-ups (from reviews)

- **VRAM peak:** `Pipeline::new` briefly allocates the raw transfer `frames`/`frame_len` on top of the
  `BatchBuffers` copies, so the peak goes above `vram_bytes` at `--batch max`. This matters on an 8 GB card.
- **Single submitter:** the transfer-queue path assumes one thread submits per `GpuContext`. This is
  documented, not enforced.
- **DX12 on Windows:** wgpu picks DX12 there, so the Vulkan-only E3 paths need the Vulkan backend pinned.
- **Block-size scope:** `lvl9s12d16seg` is validated only at ≤ 64 KiB (at 128 KiB it is below L9).

## Reproduce

```sh
B="cargo run --release -p gzc-bench --"; C="--input data/corpus --ext dds,nif"
for p in lvl9 lvl9seg lvl9s12seg lvl9s12d16seg; do $B gpu $C --preset $p --batch max --inflight 3 --out out/sp2-$p; done
$B gpu $C --preset lvl9s12seg --batch max --inflight 3 --verify --out out/sp2-verify
GZC_NO_SUBGROUPS=1 $B gpu $C --preset lvl9s12seg --batch max --inflight 3 --out out/sp2-nosg
```
