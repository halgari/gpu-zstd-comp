# Speed phase results: GPU lvl9 at 4.1–4.3 GB/s

Date: 2026-09-30 · Branch `speed` @ `559f293` (on top of M4 `8894816`) · Block 128 KiB · Budget 6144 MiB

## Headline

Full corpus (`--ext dds,nif`, 6.49 GB real bytes, 51216 blocks). RTX 5090, idle machine (load average ≈ 1.5).
MB/s are medians of 3 runs.

| Preset (algorithm) | Ratio | Start of phase (S0) | **Now** | Speed-up |
|---|---:|---:|---:|---:|
| **lvl9** (lazy2, depth 32 ≈ libzstd L9), `--batch max --inflight 3` | 1.355 | 1605 | **4107** | **2.56×** |
| lvl9, `--inflight 2` (b2860) | 1.355 | – | **4260** | 2.65× |
| rung1 (greedy, 4-byte chain, ≈ L5) | 1.343 | 1961 (M4) | 6000 | 3.1× |
| rung2 (lazy, ≈ L6), single run | 1.352 | 1788 (M4) | 4987 | 2.8× |
| lvl3 (≈ L3), single run | 1.271 | 1447 | 4836 | 3.3× |

- **Correctness:** every frame is still byte-identical to the unchanged CPU oracle. `--verify` of lvl9 passed:
  51216 frames decoded by libzstd, compressed bytes unchanged at 4,792,885,250.
- **Comparison with libzstd L9 on 8 threads of this CPU** (669 MB/s, ratio 1.3532): the GPU runs **6.1× faster**
  at a slightly better ratio. On the assumed typical 8-core PC (≈ 450 MB/s at L9, assuming 60 % of this CPU's
  per-core speed), the gap would be larger still.

## What each experiment did

Details, all runs and the rejected variants are in `docs/results/speed-log.md`.

| Step | Change | lvl9 effect | Kept |
|---|---|---|---|
| S0 | Baseline; found a real M3→M4 lvl3 regression (−6 %) | – | – |
| S1 | K2: stop the chain walk at the cap, streaming compare, `best[]` packed to one u32. **Readback staging aligned to 256 B**, which removed a 15–19 ms/batch copy penalty and explained the lvl3 regression | +21 % | ✔ |
| S2 | K1: persistent grid of L2-resident, tag-validated head tables (K1 was DRAM-bound on 410 MB of per-block tables, not barrier-bound); subgroup ballots; subgroup self-test with fallback | +21 % | ✔ |
| S3 | **Subgroup-cooperative K3** (lazy2 and greedy). Profiling showed the time went to literal scanning, not match extension. Lanes evaluate the skip sequence in parallel; cooperative match length and catch-up; lookahead window; naga loop bounding off, with a termination argument for every loop | +37 % | ✔ (two blocks per workgroup kept as opt-in `GZC_K3_BPW=2` for Ada's 24-workgroups-per-SM limit) |
| S6 | Transfer path: share input and frame buffers across in-flight slots (frees ~1 GB, so bigger batches); profiler. **No copy/compute or dispatch overlap exists on wgpu's single queue on this driver** | +7.7 % | ✔ (GPU frame packing kept as opt-in `GZC_PACK=1` for PCIe ×8 cards) |
| S5 | Cross-batch overlap | – | ✘ dropped: nothing to overlap (S6) |
| S4 | K3 no longer emits literals; K5 gathers them from (data, seqs) with a 2 KiB index; `lits` buffer removed (−128 KiB/block) | +4.7 % | ✔ |
| S8 | K2: a 15-bit fingerprint in each chain entry skips 58 % of candidates exactly, before loading any bytes; next-entry prefetch | +4.6 % | ✔ |
| S9 | K4: chunked backward FSE encode (3 lanes run the state chains, all lanes place bits), parallel table builds | +9.9 % | ✔ |

## Projection for an 8 GB-class GPU (RTX 4060 / RX 7600)

This is **a projection, not a measurement**. The target has about 7× fewer SMs than the 5090, about 6.6× less
memory bandwidth, and a 24–32 MB L2.

- **Scaling assumption:** memory-bound kernels (K1, K2, K5) scale by about 6–7×. K3 is latency-bound per block.
  On the 4060 a batch takes about 3.3 waves of resident workgroups; the S3 agent's model gives ≈ 110 ms/batch
  for K3 at this batch size. K4 scales about 7×.
- **Result:** roughly **300–350 ms of kernel time per 2559-block batch**, which is **about 0.9–1.2 GB/s
  end to end** for lvl9. The spread comes from L2 behaviour and residency.
- **Uncertain in both directions:**
  - Stage E (`GZC_K3_BPW=2`) doubles K3 residency on Ada and could cut its waves.
  - `GZC_PACK=1` saves 26 % of PCIe traffic on a ×8 link.
  - Register pressure and the absence of subgroups on some drivers could go the other way (fallback 3041 vs
    4260 MB/s on the 5090).
- **Comparison:** against an assumed typical 8-core CPU (≈ 450 MB/s at libzstd L9), the projected GPU is about
  2–2.7× faster at the same ratio. It is near, possibly just under, the 10 Gbit line at L9 quality. Presets
  rung2 (≈ L6, 1.352) and rung1 (≈ L5, 1.343) run 1.2–1.5× faster than lvl9 and would clear 10 Gbit with
  margin.
- **Next step:** measure on a real 4060/7600. Tune `GZC_K1_GROUPS` (96–128), `GZC_K3_BPW` and `GZC_PACK` (both since removed) there.

## Remaining bottlenecks and ideas

1. **K3 (47 %).** Per-warp latency-bound, with dense-sequence blocks at ≈ 2 µs per sequence (subgroup-op and L1
   latency). Further gains need fewer dependent subgroup round trips per sequence, or more blocks resident per
   SM (stage E, register trimming).
2. **K1 (24 %).** L2-bound. The best default depends on L2 size; wgpu cannot report L2 size, so choosing it
   needs a first-batch autotune (timestamps are available).
3. **K2 (16 %).** Bound by the memory sectors it touches. Further gains would come from a denser `pred`/data
   layout.
4. **Portability risks:** 64- and 128-lane subgroup paths (AMD, Qualcomm) and stage E are covered by self-tests
   and runtime guards but not by hardware runs. The WGSL for K3 is built without naga loop bounding; every loop
   carries a termination argument.

## Reproduce

```sh
B="cargo run --release -p gzc-bench --"; C="--input data/corpus --ext dds,nif"
$B gpu $C --preset lvl9 --batch max --inflight 3 --out out/s7-lvl9-i3      # ×3
$B gpu $C --preset lvl9 --batch max --inflight 2 --out out/s7-lvl9-i2      # ×3
$B gpu $C --preset rung1 --batch max --inflight 3 --out out/s7-rung1-i3    # ×3
$B gpu $C --preset lvl9 --batch max --inflight 2 --verify --out out/s7-lvl9-verify
GZC_NO_SUBGROUPS=1 $B gpu $C --preset lvl9 --batch max --inflight 2 --out out/s7-lvl9-nosg
```
