## `--batch max` is 2978, not 3125

The 6 GiB budget would allow 3125 blocks at `--inflight 3`. On the 5090, wgpu's storage bindings stop at 2 GiB, and the `pred` buffer is 704 KiB per block for `opt16p1` (11 B per position: h4 and h3 at full length, three sparse chains at a quarter each). That caps the batch at 2978. The cap does not cost anything measurable: b2900 is 0.5 % below b2978, and both fit one wave of K3 (4080 blocks).

## The recipe

`opt16p1` = `OPT16` with:

- **Candidates (S3):** the h4 chain walked 8 deep, h3 4 deep, plus three sparse chains on 6, 10 and 12-byte keys. A sparse chain holds only every 4th position and is walked 16 deep. All five chains are merged nearest-first into the same two candidate words per position as `opt16`.
- **Prices:** the Prior seed with tables retrained for S3 (`codes::OPT_PRIOR_S3_*`), plus the cover literals.
- **Parse:** one optLevel-2 DP pass, target length 32. No re-pricing passes.
- **gap3:** inner 4 KiB segments let a match start up to 3 bytes before the segment end (`opt16`: 8).
- **Top-4 pruning:** explicit-offset candidates relax only their 4 longest lengths. Repcode candidates relax all.
- **Drop pass:** after the fix-up, an explicit match of 6 bytes or less becomes literals when that is cheaper at the parse's own prices, decided per segment.

Cost of each piece, from B0 and B1: top-4 pruning costs 0.0046 % of ratio, the segment-local drop 0.00002 %.

GPU stages:
- K1 builds all five chains in one dispatch.
- K2opt does the merged walk.
- K3opt runs the single persistent pass with gap3, top-4 and the S3 prior compiled in.
- Then come `main_fixup` and the drop kernel (`k3_drop.wgsl`), and finally K5 and K4, unchanged.

## Reproduce

```sh
# Build (any target dir; this run used ~/.cache)
cargo build --release -p gzc-bench

# Verify and total bytes
target/release/gzc-bench gpu --input data/corpus --ext dds,nif --preset opt16p1 --batch max --verify
target/release/gzc-bench ref --input data/corpus --ext dds,nif --preset opt16p1 --threads 16

# Benchmark: 3 rounds, each config once per round
for r in 1 2 3; do
  for p in "opt16p1 max" "opt16 max" "opt14 max" "lvl9s12seg max" "opt16p1 2900"; do
    set -- $p
    target/release/gzc-bench gpu --input data/corpus --ext dds,nif --preset $1 --batch $2 --inflight 3 --out out/r$r-$1-$2
  done
done

# K3 split
GZC_CORPUS=$PWD/data/corpus GZC_CORPUS_BLOCKS=2978 GZC_TIMING_WARMUP=1 GZC_TIMING_PRESETS=opt16p1,opt16 \
  cargo test --release -p gzc-gpu --test k3opt k3opt_passes_timing -- --ignored --nocapture

# 4000-block corpus pipeline test (repeat with GZC_NO_SUBGROUPS=1)
GZC_CORPUS=$PWD/data/corpus cargo test --release -p gzc-gpu --test opt_pipeline -- --ignored --nocapture
```

## Follow-ups

- **Frame split.** Splitting each 64 KiB frame into several zstd blocks with their own tables gave +0.14 % ratio on top of `opt16p1` in B0 (+0.21 % on `lvl9s12seg`). It needs a K4/K5 change and was deferred.
- **AWR (anchored-window refinement, `docs/superpowers/m7/r1-parallel-parse.md`).** It starts from a lazy2 parse. Each pass then re-runs the DP in independent 512-byte windows and keeps a window only if its new parse is cheaper. Two passes reached +0.079 % over L16 at 64 KiB in research, with many more lanes than a 4 KiB segment DP. It is a candidate for the next L16-class preset and is not implemented.
- **Drop pass, 10 % of K3** (0.88 µs per block). It is latency-bound on heavy blocks: 16 serial lanes and per-byte literal atomics. Fusing it into the fix-up saved no span time in B3.
- **K1 is now the second-largest stage** for `opt16p1` (6.8 µs per block against K3's 8.2). The sparse chains' K1 cost was measured but not tuned beyond B2.
- **Batch cap.** Splitting the `pred` binding would let `--batch max` reach the budget's 3125. Expected gain is small on the 5090, since b2978 is already one wave.
- **Small cards are not measured.** On 8 GB cards a batch is several waves; A4's persistent K3 should help there.
